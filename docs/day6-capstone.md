## 🎯 Цель

За 90 минут сделать маленькую, но настоящую доработку TM: отчёт, поле, детерминацию и валидацию.
Задание проходит через все пять дней курса.

## Легенда

Логистам нужен контроль фрахтовых заказов одного типа. Возьмите тип из своей песочницы, в тексте он называется `ZFO1`.

1. Видеть в документе количество стопов, не открывая маршрут.
2. Не допускать сохранения FO этого типа без перевозчика.
3. Получать список таких FO с ключевыми данными.

## Шаг 1. Поле (10 мин)

Добавьте append-структуру к `/SCMTMS/INCL_EEW_TOR_ROOT` с полем `ZZ_STOP_COUNT` типа `INT4`.

**Готово, если** поле видно в combined-структуре `ROOT` в BOBF и в таблице `/SCMTMS/D_TORROT`.

## Шаг 2. Детерминация (25 мин)

Создайте в `BOPF_EWB` расширение `/SCMTMS/TOR` и детерминацию на узле `ROOT`.

| Параметр | Значение |
|---|---|
| Класс | `ZCL_TM_D_STOP_COUNT` |
| Триггеры | Создание, изменение и удаление узла `STOP` |
| Момент | Before save |
| Логика | Только для `TOR_CAT` фрахтового заказа и типа `ZFO1`: посчитать стопы и записать в `ZZ_STOP_COUNT` |

Подумайте, почему выбран момент before save, а не after modify. Ответ в разборе.

**Готово, если** после изменения маршрута и сохранения поле содержит верное число стопов. У FU и FO других типов поле остаётся пустым.

Образец: [`zcl_tm_d_stop_count.abap`](../code/zcl_tm_d_stop_count.abap).

## Шаг 3. Валидация (25 мин)

Создайте валидацию согласованности на узле `ROOT`.

| Параметр | Значение |
|---|---|
| Класс | `ZCL_TM_V_CARRIER_MANDATORY` |
| Триггеры | Создание и изменение `ROOT` |
| Логика | FO типа `ZFO1` без перевозчика — ошибка с номером документа |
| Поведение | Сохранение блокируется |

Создайте класс сообщений `ZTM` с сообщением `001`: «Фрахтовый заказ &1: укажите перевозчика».
Поле перевозчика найдите в структуре `ROOT` сами. Подсказка: ищите по сокращению TSP.

**Готово, если** FO типа `ZFO1` без перевозчика не сохраняется, а пользователь видит понятное сообщение. FO других типов сохраняются как раньше.

Образец: [`zcl_tm_v_carrier_mandatory.abap`](../code/zcl_tm_v_carrier_mandatory.abap).

## Шаг 4. Отчёт (20 мин)

Доработайте отчёт из дня 3 или напишите новый.

- На входе диапазон номеров FO и тип.
- На выходе таблица: номер, тип, перевозчик, `ZZ_STOP_COUNT`, количество позиций.
- Данные читаются через BOPF API пачкой, без цикла с чтением по одному документу.

**Готово, если** отчёт на 50 документах делает константное число обращений к Service Manager, а не 50.

## Шаг 5. Проверка и разбор (10 мин)

Пройдите по чек-листу:

- [ ] Каждый обработчик начинается с фильтра по категории и типу.
- [ ] Триггеры детерминации ограничены узлом `STOP`.
- [ ] Нет `COMMIT WORK`, `SELECT` по таблицам TOR и вызовов Service Manager внутри обработчиков.
- [ ] Чтение в обработчиках идёт одним вызовом на все `IT_KEY`.
- [ ] Сообщение валидации привязано к узлу и ключу документа.
- [ ] Литералы категорий заменены константами.

<details>
<summary>Разбор: почему before save, а не after modify</summary>

Количество стопов нужно только в сохранённом документе. При планировании стопы меняются десятки раз подряд. Детерминация after modify пересчитывала бы поле на каждом шаге. Before save выполняется один раз перед записью.

Обратная сторона: до сохранения поле на экране показывает старое значение. Если пользователю нужно видеть число сразу, выбирают after modify и принимают цену в производительности.
</details>

<details>
<summary>Разбор: почему валидация, а не проверка в BAdI или PPF</summary>

Валидация — часть модели. Она срабатывает при любом способе изменения: из интерфейса, из планирования, из интерфейса интеграции, из вашего отчёта. Проверка в отдельном BAdI сработает только на том пути, где этот BAdI вызывается.
</details>
